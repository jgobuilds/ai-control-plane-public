# RCPS — CI failures, 2026-07-26

Root-cause and preventive-solution review, prompted by "there have been a lot of
CI failures." Written from the run history, not from recollection — the
recollection was wrong in two places and the data corrected it.

## What actually failed

14 failures in the last 30 runs per repo across seven repos.

| Repo | Failures | What they were |
|---|---|---|
| the kit repo | 7 | `validate-kits`, **7 for 7 — it had never once passed** |
| `ai-control-plane` | 5 | all one deliberate proof PR (#3), intentionally red |
| `verdantground` | 2 | vendored files rejected by that repo's linter |
| everything else | 0 | — |

So "a lot of CI failures" is really **one gate that never passed, failing
silently for seven commits**, plus two self-inflicted by a fleet sweep. That is
a much narrower problem than the raw count suggests, and a worse one: a gate
that has never been green carries no signal at all.

## Cause 1 — a tracked generated file (the 7)

`validate-kits` re-runs the site generator and fails if the committed render
drifts. Correct gate. But `method/tools/__pycache__/build_site.cpython-314.pyc`
was **tracked**, so every run rewrote the bytecode and the diff fired. No commit
could ever have made it pass.

`__pycache__/` was already in `.gitignore` — added in an earlier commit for
exactly this reason. **`.gitignore` has no effect on files git already tracks.**
The rule looked applied and did nothing; `git rm --cached` was the missing half.

Two of the three tracked `.pyc` files were added by *this* session's sweep, via
a `git add -A` — the practice our own change-safety lens prohibits, in a file
read earlier the same day.

## Cause 2 — nobody was told (why it survived 7 commits)

`validate-kits` was the one workflow in the fleet without a `notify` job. Six
other workflows had one. A red build nobody sees is indistinguishable from no
build, and it stayed invisible in precisely the place the alerting existed for.

## Cause 3 — the environment that runs it is not the one that wrote it (the 2)

The sweep vendored files that one repo's `ruff format` wanted to rewrite and
another's `ruff check` rejected. Both green locally. Same shape as the
`pii_scan` defect found earlier the same day: `text=True` decoded staged blobs
with the Windows locale codepage, so a non-ASCII allowlist entry silently
stopped matching and a **security gate failed open** — invisible from the
machine it was written on.

## The near-misses matter more than the failures

Most of the day's defects never reached CI, because a hook, a push-protection
rule, or a deliberate proof PR caught them first. They share one root:

> **A result was verified in the environment that produced it, and reported as
> if verified everywhere.**

- known-cause corpus asserted rows that existed only in the home repo — green
  here, red in five others
- GitHub push protection rejected a secret-shaped literal our own gate had
  allowed, on the one public repo
- a regex sweep edited five workflow files and was not re-parsed; all five broke
- a signature widened from one sample then fired on a *successful* run

## The one that matters most: I diagnosed from a story, not the evidence

Investigating Cause 1, I concluded it was line endings, wrote it up, committed
it, and pushed. It was wrong. The check that "proved" it piped `git show`
through `od -c` and grepped for `\r` — matching od's own escaping of the
characters `\` and `r`, not carriage returns in the blob. `git cat-file -p`
showed LF all along.

The real evidence was **one line the CI log had already printed**, naming the
exact file. I had a plausible story and stopped looking.

This is the failure mode the diagnostician is built to refuse — it reports
"unrecognised failure" rather than guessing, because a confident wrong cause
costs more than no cause. The tool held that line; its author did not.

## Preventive actions

Mechanisms, not intentions. An intention is what we already had.

| # | Action | Status |
|---|---|---|
| 1 | `notify` + diagnostician on **every** workflow, fleet-wide (11 jobs, 7 repos) | done |
| 2 | Promote both causes to the shared table: `gitignored-but-still-tracked`, `render-drift-gate-fires-on-generated-artifact` | done |
| 3 | Assert the **negative** case for every signature — a clean run must claim nothing. A signature written from one sample describes that sample. | done |
| 4 | Vendored corpora run in each repo's CI; a vendored file nobody runs has silently rotted | done |
| 5 | Mechanical multi-file edits must **re-parse before writing**, and refuse on failure | done (the tool that broke five files was replaced by one that verifies) |
| 6 | A gate that has **never passed** should be reported as unconfigured, not failing | **open** — see below |
| 7 | Run a vendored change in every target repo before pushing any of them | **open** — done by hand this time; should be a script |

### Action 6 is the one with teeth

`validate-kits` failed 7/7. A first-run failure and a regression look identical
in a run list, and they need opposite responses: one means the gate was never
satisfiable, the other means something broke. The diagnostician already draws
this distinction for logs (`no-log` vs `escalate`); it does not yet draw it for
gates.

The check is cheap — has this workflow ever concluded `success`? — and it turns
"red again" into "this has never been green, so the gate is the suspect, not the
commit."

## What this review changed about the count

Of 14 failures: 5 were deliberate, 7 were one unsatisfiable gate, 2 were one
sweep. The instinct to read a failure count as a quality signal was wrong here.
**What mattered was not how many builds were red, but that one had never been
green and nothing said so.**
