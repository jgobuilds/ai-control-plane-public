The AI Control Plane, and the lenses that review it

A governance layer for agent work: work enters through one router, splits across cost tiers and isolated scopes, and leaves only through verified exits that a human signs off. The goal is to hand agents real work and still be able to say what they did, why, and for whom.

How work flows

One path, in order. Each step is a place policy lives, and none of them can be skipped: only the router can reach a runner.

  1. Entry through n8n

    Schedules, triggers and approval gates. n8n calls POST /route on the router and nothing else.

  2. Deterministic first

    Well-defined tasks are answered by rules in router/rules.js with no model call. A model is the fallback, not the default.

  3. Cheapest model that can do the job

    Each task type maps to a tier. A hard maxTier cap blocks frontier-model spend in automated lanes unless a call explicitly opts in.

  4. Action binding

    The router decides which verb a task may perform, from a named list per scope (for example “invoice the customer”). The task’s own claim doesn’t count. Irreversible actions at high risk force human approval, which gives segregation of duties.

  5. Firewalled runners

    Each runner reaches only its own vendor and shells out to that vendor’s CLI (claude -p, gemini -p). Its tools are narrowed to what the bound action needs. The PII vault stays in the scrubber and is never mounted into a runner.

  6. Hash-chained ledger

    Every decision is appended with tier, model, reason, cost, declared action and bound tools. No path acts without leaving a record.

  7. Gated exit

    Deliverables leave only through human-gated steps. Cross-checks run the reviewer on the other vendor.

Cost, stated plainly

Since 2026-06-15, headless claude -p on a Claude subscription draws on a per-user monthly Agent SDK credit ($20 Pro · $100 Max 5x · $200 Max 20x) at standard API rates, not on plan usage limits. When the credit runs out, requests stop unless usage credits are enabled. Unattended work is a capped cost line, not a free entitlement. The design doesn’t depend on it: the router picks the tier, so a change in vendor terms moves the cost, not the architecture.

Operating rules

These hold across the codebase, and each one is enforced by a check rather than just written down.

A control isn’t enforced until you’ve watched it fail
Every gate is broken on purpose before it’s trusted. “Inconclusive” is never a pass.
A failure that happens twice is a harness bug
CI failures are matched against a list of known causes before any model is asked. A new diagnosis becomes a new known cause, and repeats are counted in reliability/recurrence.yaml.
Quote it or don’t claim it
Sources are saved to a file and quoted by line number. “Could not confirm” is a valid finding. A claim that has been retracted is registered, and CI fails if it reappears.
Decisions get an ADR
19 so far. Each keeps the options that lost, plus a Cost column that CI checks for.
Pins move by policy
Every image and agent CLI is pinned. Version updates wait 7 days, security fixes don’t wait, and an eligible upgrade must be taken within 30 days. Deploys go to one canary runner first, then observe, then promote.

How lenses work

A lens is one review angle, written as a short markdown reference in ai-standards/references/. Each lens is a list of rules, and every rule has the same three parts. The failure behind it is named, because a rule with no real failure behind it gets argued with.

change-safety.mdVerify the outcome
RiskReporting “pushed” from the command that ran, not the state it left behind. A multi-file git add once failed on a missing file, nothing was staged, and five repos were reported as pushed while showing the old hash.
CheckAfter any state change, confirm the state: HEAD moved and git status is clean; origin/main..HEAD is empty; the deleted thing is gone and nothing still references it.
FixConfirm the resulting state, then report it. “I ran X” and “X happened” are different claims.

Wiring a repo to lenses

Each repo lists the lenses it wants. When the engineering-standard skill reviews that repo, it loads only the lenses named here, reading each one as needed rather than all at once. Every finding must give file:line, what, why it matters, and the fix. A finding without a fix is just a complaint.

# .engineering-standard/config.yml
overlay: ../ai-standards
lenses: [pragmatic-principles, design-patterns, code-smells,
         change-safety, proving-controls, cost-awareness, ...]

Adding a house lens

Ask: what review comment do I keep making? That comment is a lens. Write it as risk → check → fix with a real failure named, and say whether it’s binding or advisory, because an agent can’t tell from tone.

From lens to gate

A lens is judgment that gets applied at review time. Once a rule is mechanical enough, it gets promoted to a script and a CI check, and from then on it’s enforced rather than just advised.

LensBecame
dependency-securityPin checks (image:tag@sha256), a 7-day Dependabot wait, a weekly job that flags stale pins, and a daily scan of the images the stack actually runs
cost-awarenessThe Cost column required in every ADR options table (adr_check.py)
pii-controlsCommit gate, commit-message gate and CI scan in every repo
proving-controlsMutation tests next to each gate; tool-restriction probes that decide from the CLI’s own tool list
evidence-standardfetch_source.py quote-by-line, and the retracted-claims check

A limit worth stating: overlay: is a filesystem path, so it only resolves where ai-standards sits next to the repo on disk. That’s why each repo’s own AGENTS.md still has to carry everything a contributor needs.

Maturity and ramp

Self-assessed on 2026-09-24, against our own scale. Nobody outside the project has reviewed it. Each level is a claim about evidence, not about effort, and the full table with the command behind every row is in docs/design/MATURITY.md.

1Ad hocNothing written, nothing enforced.
2DocumentedWritten down and followed by habit. Nothing fails when it is violated.
3EnforcedA check fails on violation. Nobody has confirmed the check can fail.
4ProvenThe check has been watched failing on purpose, and the proof re-runs automatically.
5Proven at scaleSustained evidence from real volume, plus outside review. Deliberately out of reach here.

Overall: enforced, thinly exercised — real controls, little traffic.

DimensionLevelWhy not higher
Policy at one chokepoint4Tools are bound to a request’s governing verb, and the CLI flag behind it was probed live and watched refusing — but almost no bound traffic has flowed yet.
Auditability4Hash-chained ledger, verified before use; ~100 decisions total, so a tamper test proves less than it would at scale.
Supply chain & change safety4Pins, release-age and staleness rules, daily scans of the images we build, canary deploys. Each gate watched failing; the deploy path has run few times.
Isolation & data protection3Scope isolation and the PII vault are tested, but the retention sweep still deletes nothing.
Reliability & diagnosability3Recurrence register with proofs the gate re-runs; behaviour under sustained failure untested.
Cost governance3Tier ceiling enforced and cost required in every decision record; the spend data is too thin to judge the tier mix.
Compliance evidence3Framework map generated from the enforced config, honestly mostly “partial”, and self-rated.
Security posture322 tracked findings: 11 closed with proofs, 5 partial, 5 open, 1 accepted.
Quality eval23 eval cases. No semantic gate over real data yet.
Autonomy2Assisted and parallel work today; the supervised-autonomy lanes are built but idle, so the rung is not reached.

The ramp

  1. Make deletion real

    Take the retention sweep out of dry-run, behind a signed deletion certificate and a restore test. Moves data protection to 4.

  2. Grow the eval corpus

    To 30 cases per scope from real captured failures, then measure run-to-run noise before gating anything on it. Moves quality eval to 3.

  3. Let one lane carry real work

    End to end: a real ticket claimed, the action bound, a human gating the exit. Moves autonomy to 3.

  4. Close the open security findings

    Isolation first, each closed finding naming a proof the gate runs.

  5. Earn volume, then re-score

    Everything at 4 stays at 4 until real traffic tests it. That, plus an outside reviewer, is the only route to 5.

What stays private, and what doesn’t

The engine is public and AGPL. Three things are held back, and none of them is a control:

Tenant and org content
The real scope tree, org identity, prompts and client context live in a private overlay. A hygiene gate enforces their absence here on every commit, and over the whole tree in CI.
Secrets
Never in the repo in any form. Tokens are per-service and held outside version control; decision records carry types and counts, never values.
Commercial analysis
A strategy document about ourselves isn’t part of the engine. The gaps are public anyway, as issues — that’s the half that matters if you’re evaluating this.

The mechanisms are public on purpose: a control that only works while its design is secret isn’t a control.
